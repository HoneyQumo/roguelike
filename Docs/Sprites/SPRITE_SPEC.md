# Спрайт-листы · технический контракт и мастер-промпт

Проект: 2D top-down шутер, C++ / SFML 2.5.1
Все десять этапов закрыты, сверх них добавлены вид оружия сбоку, вторая
атака ближнего боя и смена оружия. Выгрузка сведена в атласы, референс
интеграции скомпилирован и прогнан на SFML.

---

## 1. Закреплённые решения

| Решение | Значение | Почему так |
|---|---|---|
| Поворот | свободный 360°, `sprite.setRotation()` | один набор кадров вместо восьми; точное прицеливание мышью |
| Кадр тела | 64 × 64, пивот **(32, 32)** | персонаж ~38 px — различимы 11 стволов |
| Кадр оружия | 160 × 64, пивот **(80, 32)** | вмещает РПГ; пивот совмещён с пивотом тела |
| Направление | взгляд **вправо (+X)**, `angle = atan2(dy,dx)·180/π` | 0° = вправо, как отдаёт atan2 — никаких поправок в коде |
| Слои | `body` → `weapon` (оружие поверх) | 2 текстуры, 2 draw-call на персонажа |
| Кисти | **запечены в спрайт оружия** | правильное перекрытие «кисть поверх ствола» без третьего слоя |
| Стойка | одна на все стволы | тело рисуется один раз на всю игру |
| Свет | омни (светлее к центру) | направленный свет «поедет» при повороте |

## 2. Контракт хвата — НЕ МЕНЯЕТСЯ

Всё в пикселях кадра тела 64 × 64.

```
пивот                 (32.00, 32.00)
ведущая кисть         (44.80, 45.76)   ← пистолетная рукоять
поддерживающая кисть  (55.20, 41.60)   ← цевьё
ось ствола            y = 44.16        ← проходит под правым плечом
корпус развёрнут      26°   (блейдовая стойка)
таз развёрнут         12°
голова                 0°   (строго на цель)
```

Каждый новый ствол рисуется так, чтобы его перчатки легли **ровно в эти две точки**.
Это и есть «универсальная стойка»: тело не меняется никогда, меняется только геометрия
ствола вокруг фиксированных кистей.

Если анимация двигает кисти (перезарядка, удар, кувырок) — в `character.json`
для каждого кадра выдаётся `hand_anchor`, и слой оружия смещается на эту дельту.

## 3. Два комплекта на одном риге

Скелет, стойка, тайминги и контракт хвата — общие. Различаются только слои
экипировки и палитра. Любая анимация рисуется один раз и работает для обоих.

**ГГ — бронированный комплект**

| Слой | Значение |
|---|---|
| Шлем | `sensor` — гранёный купол, гребень с эмиссионной линией, сенсорный блок |
| Лицо | **не рисуется**: вместо клина кожи циановое забрало (оно же указатель направления) |
| Наплечники | `angular`, радиус 3.9 |
| Нарукавники / налокотники | есть, золото с циановой линией |
| Нагрудник | сегментированные плиты по корпусу |
| Корпус | графит · накладки золото · шлем сталь · поддоспешник тёмно-синий |

**Противник — мягкий комплект**

Каска, разгрузка, рукава, открытое лицо. Ни одного элемента брони.
Перекрашивается двумя рампами:

```
ACC_D #6C261E   ACC #A33A2A   ACC_L #CC6042     ← корпус  = цвет фракции
SLV_D #3E2E24   SLV #604838   SLV_L #82644E     ← рукава
```

Новый противник = 6 значений цвета. Ни одного нового кадра.

**Палитра.** Замкнутые рампы по 3 тона. Каждая деталь снапится **только к своей
рампе** — поэтому золото накладок никогда не даст грязных пикселей на графите.

## 3б. Ноги — только в движении

Из строго верхней точки стопы стоящего человека закрыты плечами, поэтому в риге
`show_feet=False` **по умолчанию**: в статике, в `idle` и в `shoot` ног нет.
Включают их только `walk` и `run`.

Это не только анатомия. Появление ног работает бесплатным индикатором
состояния: «видны ноги» = «персонаж движется». В топ-дауне, где всё читается
силуэтом, это даёт игроку понять, кто из противников уже двинулся, без единого
нового спрайта.

Чтобы вход в движение не «щёлкал», стопы в **нейтральной фазе цикла спрятаны
под корпусом**: на `walk к0` и `run к0` ног не видно, они выезжают только на
размахе шага. Переход покой → шаг получается непрерывным.

## 4. Раскладка сводных атласов

Выгрузка сведена в четыре текстуры. Отдельных PNG на анимацию больше нет:
было 110 файлов, стало 13. Каждый лишний файл — отдельный биндинг текстуры
в кадре, а на экране одновременно десяток противников, их оружие, кровь под
каждым трупом и пачка эффектов.

```
player.png        768 x 1152   0-7 общие анимации, 8 мощная атака,
                               9 смена оружия, 10-17 направления кувырка
enemy_<тип>.png   768 x  512   те же строки 0-7; ни кувырка, ни строк 8-9
weapons.png       640 x  704   вид СВЕРХУ: строка = ствол, столбец = хват
weapons_side.png  224 x  352   вид СБОКУ: лут на полу, инвентарь, HUD
fx/fx.png         640 x  296   эффекты полосами, прямоугольники в JSON
```

Строки, которые есть только у ГГ (мощная атака и смена оружия), добавлены
**после** общих восьми и **перед** кувырком. Так раскладка противников не
сдвигается: их текстуры не пришлось перевыгружать ни разу, а код, читающий
строки 0-7, продолжает работать без правок. Это правило для всех будущих
строк ГГ.

Кадр везде 64 × 64, поэтому `textureRect` считается прямо из индексов:
`{col * 64, row * 64, 64, 64}`. Таблица поиска не нужна.

| Строка | Анимация | Кадров | мс | Луп |
|---|---|---|---|---|
| 0 | idle | 6 | 175 | да |
| 1 | walk | 8 | 110 | да |
| 2 | run | 8 | 75 | да |
| 3 | shoot | 4 | 60 | нет |
| 4 | reload | 12 | 90 | нет |
| 5 | melee | 6 | 60 | нет |
| 6 | hurt | 3 | 80 | нет |
| 7 | death | 8 | 110 | нет |
| 8 | heavy — мощная атака, только ГГ | 12 | `frame_ms` | нет |
| 9 | swap — смена оружия, только ГГ | 10 | `frame_ms` | нет |
| 10–17 | roll, строка = направление | 10 | 50 | нет |

Столбцы `weapons.png`: 0 обычный, 1 без поддерживающей перчатки,
2 без перчатки и магазина, 3 без перчаток вовсе. Перезарядка переключает
столбец по кадрам; столбец 3 нужен там, где ствол существует сам по себе,
без рук — убранный за спину, на стойке, в витрине.

Эффекты пакуются **полосами, а не общей сеткой**: у вспышки кадр 32 × 24,
у лужи крови 64 × 64, у пули 24 × 8. Общая сетка по максимуму раздула бы
текстуру пустотой в несколько раз. Прямоугольник каждой группы лежит
в `character.json` → `atlas.fx.rects`.

## 4б. Обратная связь стрельбы

До этого у выстрела была только дульная вспышка: игрок видел, что выстрелил,
но не видел, попал ли. Добавлено:

| Ассет | Кадр | Как ставить |
|---|---|---|
| `bullet` | 24 × 8, пивот (2,12) | три вида: винтовочный, пистолетный, дробь. Один кадр, поворот на угол полёта |
| `impact` | 24 × 24, пивот (4,12), 4 кадра, 40 мс | искры от попадания в стену, поворот на угол нормали |
| `explosion` | 64 × 64, пивот в центре, 7 кадров, 55 мс | взрыв РПГ. Единственный ассет, которому угол безразличен |
| `shell_fly` | 12 × 12, 4 кадра, 60 мс | гильза крутится, поэтому четыре кадра, а не один спрайт |
| `rocket` | 28 × 12, пивот (4,6), 2 кадра | ракета в полёте, факел пульсирует |

Искры рисуются **без обводки**. С обводкой 0.62 на искре радиусом в пиксель
от неё остаётся один тёмный контур — на кадрах вместо брызг огня получался
чёрный мусор.

Дым взрыва идёт **по краю огня и наружу**, а не поверх него: первый заход
клал тёмные шары внутрь пламени и получались дыры в огненном шаре. Ровно та
же ошибка, что была с тёмной кромкой внутри лужи крови.

## 4в. Подбираемое и интерфейс

`pickup` — аптечка, ящик патронов, пластина брони. Кадр 24 × 24, пивот
в центре, **поворот не применять**: лежащий предмет не должен доворачиваться
за прицелом. У каждого два кадра — обычный и подсвеченный; подсветку движок
включает, когда игрок в радиусе подбора. Это надёжнее мигания цветом и
работает одинаково на любом полу.

### Оружие сбоку — `weapons_side.png`

Кадр 112 × 32, пивот в центре, строка = тот же ствол, столбец 0 обычный,
1 подсвеченный. Одним набором закрыты три применения: лут на полу,
инвентарь, HUD.

**Почему отдельный набор, а не поворот вида сверху.** Сверху у пистолета
не видно ни рукояти, ни спусковой скобы, ни магазина — силуэт вырождается
в палку, и в инвентаре глок неотличим от ножа. Профиль показывает ровно
то, чем стволы отличаются друг от друга. Первая версия иконок собиралась
обрезкой видов сверху; она и была заменена этим набором.

**Масштаб общий с видом сверху.** Профили рисуются в тех же авторских
координатах и тем же `SCALE`, поэтому АК на полу ровно такой же длины,
как АК в руках. Автопроверка сравнивает длины по обеим текстурам.

**Подсветка — ободок, а не перекраска.** У стволов разные материалы, и
осветление корпуса на дереве и на вороненой стали читается по-разному.
Столбец 1 = светлый ободок под тёмной обводкой, материалы не тронуты.

**Поворот не применяется.** Дробный угол рвёт пиксельную сетку; для
разнообразия достаточно отражения по X. Рисовать лут ДО тел.

Два правила, вылезших при отрисовке профилей и не встречавшихся сверху:

* Сбоку у ствола появляется **крупная сплошная плоскость**, которой
  сверху не было. На тёмном базовом тоне (`POLY_D` почти совпадает с
  цветом обводки) все внутренние линии на ней пропадают, и пистолет
  превращается в чёрный комок. Базовый тон профиля — средний, тёмный
  уходит в линии.
* **Спусковая скоба — кольцо**, и сплошным пятном она слипается с
  рамкой. Просвет заливается цветом `OUT`: он входит в рампу, снап его
  не портит, и на любом полу он читается одинаково. Это тот же закон
  «тёмное под светлым читается как дыра», что стоил переделок тени,
  лужи и дыма, — здесь он впервые работает НА нас: дырка и должна быть
  дыркой.

`side_bbox` в `weapons.json` — занятый прямоугольник внутри кадра.
По нему интерфейс обрезает рамку под инвентарную ячейку, не зашивая
размеры стволов в код. Масштабирования нет нигде: оно рвёт сетку.

## 4г. Две атаки ближнего боя

Быстрая — строка 5 `melee`, 6 кадров по 60 мс, дуга слоя оружия
+34° → −52°. Мощная — строка 8 `heavy`, 12 кадров, заряжаемый удар сверху
с шагом. Строка 8 есть **только у ГГ**: раскладка противников не сдвинулась,
их текстуры перевыгружать не пришлось.

**Покадровый тайминг.** Единственная анимация набора, где одной длительности
на строку мало. Занос идёт по 85–110 мс, удар по 34 мс, и именно этот
контраст читается как вес. При равномерном тайминге мощный удар выглядит
как быстрый, только длиннее — это проверялось, разница очевидна. Поле `ms`
у строки оставлено средним, чтобы старый код не делил на ноль, но читать
надо `frame_ms`.

**Две петли удержания, а не одна.** Кадры 3–4 — набор заряда, 5–6 — заряд
набран. Игрок должен видеть, когда копить дальше бессмысленно; переход
между петлями — единственное, что об этом сообщает. Удержание НЕ растягивает
кадр, а повторяет петлю: растянутый кадр читается как подвисшая игра,
повтор — как накопление.

**Свечение «заряжено» новых кадров не потребовало.** Движок пульсирует уже
готовым `fx/hit_flash.frag` на амплитуде 0.22 — тем же шейдером, что рисует
белую вспышку урона, и по той же причине, по которой вспышка не запекалась
в кадры: она нужна поверх любого кадра.

**Бюджет вылета — главное, что вскрылось на этой анимации.** Инвариант
набора: ни один пиксель тела не дальше 32 px от пивота и не касается
границы кадра. В стойке **поддерживающая** кисть уже стоит в 25 px от
пивота — она, а не ведущая, упирается в потолок первой, и свободного хода
вперёд остаётся меньше 3 px. Первая сборка концептов вылетала за кадр на
двенадцати кадрах из сорока четырёх именно по рукам.

Отсюда разделение, которого в прошлых анимациях не было:

* вынос **кистей** вперёд — дорогой. В итоге нулевой: всё, что помещалось
  в бюджет, давало меньше пикселя и при этом уводило слой оружия на дробную
  позицию, что на пиксель-арте хуже отсутствия эффекта.
* вынос **корпуса**, головы, локтей — дешёвый: корпус широкий, но сидит
  близко к пивоту, до границы ему далеко.
* **таз и задняя нога назад** — бесплатный, и он удлиняет силуэт в противоход
  корпусу, поэтому фигура остаётся отцентрованной на пивоте.

Вес удара несут не руки, а размах слоя оружия (у него свой кадр 160×64,
граница ему не мешает), скрутка корпуса против таза, контраст тайминга и
реальное смещение персонажа по миру.

**Кадр удара должен стоять на проходе оружия мимо взгляда.** В первой сборке
дуга прыгала с +34° на −58°, то есть проносилась мимо «прямо перед собой»
между кадрами, и кадра самого удара в анимации не было — только замах и
пронос. Кадр 8 переставлен на −20°.

**Тремор на заряде — ровно 1 px.** Идёт через `dx/dy`, то есть в авторских
координатах до даунсемпла, и тем же числом смещается слой оружия. Сдвиг
готового спрайта на дробный пиксель порвал бы и сетку, и контракт хвата.

**`move_speed` в петлях нулевой.** Иначе персонаж уезжает всё время, пока
игрок копит заряд. Проверяется assert'ом в `heavy.py` и сверкой в
`qa_check.py`.

Отклонённые концепты лежат в `melee2.py` вместе с мотивировкой: круговой
замах (единственный площадной, но ножу не идёт), выпад одной рукой
(сближение с уроном; там же показано, как снятие кисти со ствола —
столбец 1 — втрое увеличивает бюджет вылета ведущей руки).

## 4д. Смена оружия

Строка 9, 10 кадров, 545 мс. Только у ГГ.

**Анимация нужна не для того, чтобы поменять спрайт.** Оружие — отдельный
слой, сменить ствол технически значит поменять строку в `weapons.png`, это
ноль кадров. Анимация нужна, чтобы у смены была ЦЕНА. Здесь цена — 265 мс
с пустыми руками, и это видно: перезарядку такой сменой уже не отменишь.
Отклонённые концепты в `swap.py` различаются ровно этим — что именно смена
отнимает у игрока: время (Б), точность (В), ничего (А).

**`swap_frame` внутри окна `weapon_hidden`.** Подмена спрайта на видимом
кадре читается как рывок, поэтому строка меняется там, где слоя оружия на
экране нет вообще.

**Убранный ствол — отдельный слой, а не часть кадра тела.** Иначе на
каждый ствол пришлось бы по своей строке смены.

Здесь вылезли две ошибки, обе из уже знакомого класса:

* Сначала на этих кадрах стояла готовая 16×16 заглушка `stowed` из
  `fx.png`. Сравнение **в натуральную величину** показало, что она
  неотличима от «не рисовать ничего»: 7 px в поперечнике, почти целиком
  тонет в броне. Для кувырка, где ствол прижат к груди, она правильная;
  для смены — нет. Отсюда столбец 3 в `weapons.png` (без перчаток вовсе):
  в столбцах 0–2 перчатки запечены, и на бесхозном стволе они читаются
  как тёмные комки.
* Якоря убранного ствола сначала стояли в 6–11 px от пивота, то есть
  внутри тела: из спрайта оставалось около 60 видимых пикселей тёмного
  среди тёмного. Тот же закон, что стоил переделок тени, лужи и дыма.
  Якоря вынесены за силуэт корпуса.

**Угол убранного ствола меняется по кадрам.** При одном фиксированном угле
ствол только ехал вместе с персонажем и выглядел приклеенным; доворот от
«поперёк корпуса» к «вдоль спины» читается как закид на ремень.

**Доворот плеч (`TROT`) — главный силуэтный рычаг там, где оружия в руках
нет.** Без него четыре кадра пустой фазы отличались на 250 px и читались
как зависшая игра; с ним минимум по строке 992 px.

## 5. МАСТЕР-ПРОМПТ

Копируй блок, подставляй параметры анимации из таблицы выше, присылай мне.
Всё, что в разделе «не менять», я не трогаю — иначе кадры разъедутся между собой.

```
ЭТАП: анимация <ключ> (<название>)
```

## 7. Ключевые заметки по анимациям

**idle (6 кадров, 175 мс)** — ✅ утверждено (переутверждено после снятия ног). Ключевое решение: **кисти и
оружие в кадре неподвижны**, `weapon_offset = (0,0)` на всех кадрах. Дышит корпус
вокруг них: передняя доля груди расширяется, плечи доворачиваются на 0.45°,
голова идёт с фазовой задержкой в четверть цикла, таз контрит переносом веса.
Таз и стопы зафиксированы намертво — если дышит весь корпус, силуэт «надувается»
и на диффе меняется вся кромка вплоть до ботинок.


**walk (8 кадров, 110 мс)** — 🔸 на согласовании. Из строго верхней точки ноги
закрыты плечами, поэтому вынос стопы за силуэт даёт тёмную полосу, читающуюся как
второй ствол за спиной. Ноги убраны под корпус; ходьбу несут качание корпуса
**поперёк** движения (±1.6 px), встречный доворот таза (±9°) и плеч (±3°) и
просадка оружия на 1 px в момент касания. Касаний два за цикл — у просадки
двойная частота.

Первая анимация со сдвигом слоя оружия: `weapon_offset` в `character.json`
даёт по кадру `[0,0] [0,1] [0,0] [0,-1] …` — повернуть на угол прицела и
прибавить к позиции персонажа.

**Стрейф — принят вариант А:** один цикл на все направления, включая движение
боком и назад. Строк `walk_side` / `walk_back` не будет. В движке темп
проигрывания стоит привязать к скорости, иначе медленный стрейф выглядит
как маршевый шаг.

**run (8 кадров, 75 мс)** — 🔸 на согласовании. Бег обязан отличаться от ходьбы
**на стоп-кадре**: корпус вытянут вперёд, голова обгоняет плечи, оружие опущено
в низкую готовность постоянным сдвигом слоя на 3 px вниз. Поверх него та же
просадка на касание, отсюда `weapon_offset` вида `[0,3] [0,4] [0,3] [0,2] …`.
Шаг шире, встречный доворот таза 12° против 9° у ходьбы.

**roll (10 кадров × 8 направлений, 50 мс)** — 🔸 на согласовании.
Направленный рывок: **толчок (к0–к1) → распластанный полёт (к2–к4) →
группировка (к5) → перекат (к6–к7) → вставание (к8–к9)**. Только ГГ.

**Направление считается ОТНОСИТЕЛЬНО ПРИЦЕЛА, не относительно мира.**

```cpp
float rel = std::atan2(move.y, move.x) - std::atan2(aim.y, aim.x);
int   row = ((int)std::lround(rel * 4.f / 3.14159265f) % 8 + 8) % 8;
```

Восемь строк покрывают все направления мира непрерывно, ствол всё уклонение
остаётся на цели. Атлас — отдельная текстура 640×512: строка = направление,
столбец = кадр.

### Полёт: распластанная поза и три новые детали

Руки вытянуты по направлению рывка, ноги прямые назад, подошвы развёрнуты
в камеру. Поза потребовала того, чего в риге не существовало:

| Деталь | Почему её не было | Как сделана |
|---|---|---|
| **Кулак** | кисти запечены в слой оружия — в стойке их нет вовсе | `hands="both"`, `fist=2.1`: перчатка, большой палец, золотая накладка на костяшках (`knuckle`) |
| **Подошва** | стопа в стойке всегда прижата к полу | `sole=True`: каблук, протектор двумя полосами, новый тон палитры `BOOT_L` |
| **Прямая рука** | в боевой стойке рука всегда согнута | локоть ставится строго на линию плечо-кисть |

Подошва рисуется только вместе с `feet_on_top`: под голенью её всё равно
не видно. Это проверяется assert'ом.

**Что пришлось убрать, чтобы поза читалась.** Первый прогон растягивал сам
корпус до 9.8 — руки не вылезали за его контур и не читались вообще. Корпус
ужат до 6.6, вся длина ушла в конечности. Кисти разведены на 6.2 поперёк
рывка: при 4.8 руки проходили ровно под головой и она их закрывала. Налокотник
и нарукавник с вытянутой руки снимаются (гасятся резче остального множителем
1.6): на 19 пикселях длины они превращали конечность в цепочку золотых крошек.
Наплечник остаётся — это опознавательный знак ГГ.

Три состояния тела, между которыми интерполируется всё: `BASE` (стойка),
`DIVE` (полёт), `TUCK_S` (группировка). Стопы заданы **явной таблицей**
`FOOT_AL`/`FOOT_SD`, а не смесью состояний: в перекате они описывают дугу
через верх корпуса, и формула из этой дуги делала два почти одинаковых кадра.

**Ствол на к1–к7 не рисуется.** Пока полёт был «шаром», прижатый к груди
силуэт работал; с вытянутыми руками ему негде лежать — между кистями он висит
в воздухе, на корпусе ложится тёмным брусом поперёк нагрудника, а развернуть
его вдоль руки нельзя. Ствол в руках на к0, к8, к9; за спиной 0.35 с.

**Высота без тени.** Тень отклонена заказчиком, и сравнение трёх вариантов это
подтвердило: сверху тело шире собственной тени и просто её закрывает. Полёт
держат распластанный силуэт, оторванные от пола подошвы и подрост тела на 5%.

Подрост **запечён в кадры** через `body_scale` → `Layer.k`, то есть в авторские
координаты до даунсемпла. `setScale` на готовом спрайте делать нельзя.
**Инвариант, проверяется assert'ом:** `body_scale != 1.0` только на кадрах,
где ствол скрыт — слой оружия за телом не тянется.

Новое в `character.json`:

| Поле | Что это |
|---|---|
| `move_speed` | доля пиковой скорости рывка по кадрам: `0.10 0.55 1.00 1.00 0.92 0.66 0.46 0.30 0.10 0.00` |
| `invuln_frames` | `[2,3,4,5,6,7]` — кадры неуязвимости, значение геймплейное |
| `phases`, `direction_names`, `row_formula` | раскладка строк и фаз |

**hurt (3 кадра, 80 мс)** — 🔸 на согласовании. Флинч намеренно
**не направленный**: за 240 мс сторону удара не прочитать, её несёт
отбрасывание персонажа движком по вектору урона. Общая реакция — корпус
сжимается, плечи вжимаются (`sh_side` 9.2 → 8.5), голова уходит в них.
Ствол остаётся в руках и с прицела не сходит.

**Белая вспышка — шейдер `fx/hit_flash.frag`, а не кадры.** Вспышка нужна
поверх ЛЮБОГО кадра любой анимации: попасть могут и в ходьбе, и на
перезарядке, и в перекате. Кадрами это удвоило бы весь атлас.

```glsl
uniform sampler2D texture;
uniform float amount;
void main() {
    vec4 c = texture2D(texture, gl_TexCoord[0].xy);
    gl_FragColor = vec4(mix(c.rgb, vec3(1.0), clamp(amount,0.0,1.0)), c.a) * gl_Color;
}
```

Тем же шейдером рисуется и слой оружия. `flash = max(0, flash - dt/0.12)`.

**Брызги — `fx/blood_hit.png`**, 4 кадра по 45 мс, 32×24, пивот (6,12), летят
в +X. Ставить в точку попадания и поворачивать на угол урона, как дульную
вспышку; на попадание спавнить одну-две штуки с разбросом ±20°. Отдельно
лежит `fx/blood_speck.png` — декаль на полу, если брызги должны оставлять след.
У брызг свой таймер: они нужны поверх ЛЮБОЙ анимации, а не только hurt.

**death (8 кадров, 110 мс)** — 🔸 на согласовании. Главное: **падение сверху
показывается не смещением, а ДЛИНОЙ силуэта.** Сдвиг по экрану — это движение
по земле. Стоящий человек сверху — компактное пятно 46 px, лежащий —
вытянутая полоса 49 px, голова на одном конце, подошвы на другом. Первая
версия оседала, оставаясь компактной, и читалась как «персонаж повернулся
боком», а не упал.

Тело валится **назад от прицела**: стопы остаются примерно на месте, голова
уезжает назад, между ними разворачивается корпус. Реализовано интерполяцией
между двумя состояниями `D_UP` (стойка) и `D_DOWN` (тело на полу) плюс
кривая перелёта `DEATH_OVER` — на касании тело чуть шлёпается и подбирается.

Единственная анимация, где **ноги возвращаются**: падающее тело их
раскрывает, и без них труп читается как брошенный мешок. `legs_visible_from = 1`.

| Поле | Что делает движок |
|---|---|
| `drop_frame` = 1 | после кадра спавнит ствол объектом на полу — спрайт тот же, из `weapons/`, он и так нарисован сверху |
| `hold_last_frame` | перестать обновлять кадр, труп остаётся лежать |
| `freeze_rotation` | заморозить поворот на угле смерти, иначе труп доворачивается за прицелом |
| `glow_fade` | живое → тусклое → мёртвое |
| `blood_pool_start_frame` = 3 | с этого кадра запускается лужа |

**Лужа — `fx/blood_pool.png`**, 10 кадров по 150 мс, кадр 64×64 с ТЕМ ЖЕ
пивотом (32,32), что и тело. Движок рисует её той же позицией и тем же углом,
что и труп, просто другой текстурой ПЕРЕД телом. Свой таймер: лужа продолжает
растекаться после того, как анимация тела кончилась, и держит последний кадр.

Лужа **заметно больше трупа и смещена в сторону от оси тела**. Симметричная
лужа по размеру телу оказывается ровно под ним: в первой версии от неё
оставалось 74 видимых пикселя из полутора тысяч, тонкий ободок по контуру.
Та же ошибка, что была с контактной тенью в кувырке — сверху тело шире почти
всего, что кладут под него.

Кровь — **отдельные слои, а не кадры тела**. Режим без крови это «не рисовать
два слоя», а не второй комплект атласов. Порядок отрисовки стал:
`blood_pool → body → weapon → hand_item → muzzle_flash → blood_hit`.

**Свечение гаснет отдельными тонами палитры** `GLM_*` и `GLX_*`, а не
прозрачностью: рампы замкнутые, снап идёт по именам цветов, поэтому
полупрозрачный циан просто снапнулся бы обратно в циан.

## 7в. Типы противников

Один риг, одни анимации, один контракт хвата. **Два разных рычага**, и путать
их нельзя:

| Рычаг | Что меняет | Чего стоит |
|---|---|---|
| Перекраска | шесть значений цвета корпуса и рукавов | **ноль новых кадров** |
| Надстройка | ранец, баллоны, антенна, щит, ширина плеч — меняет КОНТУР | свой атлас на тип |

| Тип | Читается по |
|---|---|
| Рядовой | базовый силуэт, точка отсчёта |
| Штурмовик | горб ранца за спиной |
| Щитовик | плоская стена сбоку — самый узнаваемый контур |
| Тяжёлый | два бугра баллонов плюс самый широкий корпус |
| Связист | тонкая антенна наружу, единственная деталь такой формы |
| Командир | крупнее всех, гребень и золото |

**Чёрный силуэт — обязательная проверка.** Цвет в топ-дауне теряется первым:
на тёмном полу, в дульных вспышках, в куче тел. В листе согласования есть
полоса, где все шесть типов залиты одним цветом.

Первый прогон эту проверку провалил: различался только щитовик, надстройки
были слишком мелкие и целиком помещались внутри контура корпуса. Замер
свободного места показал, почему: спереди-снизу, где рука держит ствол,
до предела поворота остаётся **2.8 px**, а сзади — **12–14 px**. Все
надстройки ушли назад и вбок и стали вдвое крупнее. Отличий от базового
силуэта стало 103–377 пикселей вместо десятков.

**Размер меняется через `torso_r` и `hip_r`, а НЕ через `body_scale`.**
`body_scale` уводит кисти вместе с телом, а слой оружия за ними не тянется.
Точки хвата у всех шести типов остаются на контракте до пикселя.

**`gear_scale`** — множитель надстроек. Смерть гасит его до 0.4: труп и так
тянется на 49 px, и ранец поверх этого вылезал за кадр у трёх типов
из шести. Лежащему на спине ранец и так оказался бы под телом.

Кувырок только у ГГ — это экономит по восемьдесят кадров на тип.

## 7б. Автопроверки, которые гоняются на каждой анимации

Все прогоняются через единственный вход `anim.compose_frame()`, поэтому листы,
GIF и атлас всегда показывают одно и то же.

1. **Касание границы кадра** — ни один пиксель тела не должен лежать на краю
   64×64, иначе обводка обрежется, а при повороте появится шов. Здесь же
   ловилась старая ошибка `add_outline` на `np.roll`: обводка заворачивалась
   на противоположный край.
2. **Дифф соседних кадров** — считаем изменившиеся пиксели. Слишком мало —
   кадр-дубль, анимация залипает. Так нашлись кадры 3–4 переката.
3. **Радиус силуэта от пивота** ≤ 32 px, иначе при повороте угол вылезет
   за кадр. Сейчас максимум 31.8 px (reload).
4. **Перчатка на запястье** — проба пикселей в точках хвата: слой оружия
   и слой тела не должны разъезжаться.
5. **Три пола** — тёмный `#14161B`, средний `#3A3F4A`, светлый `#9AA3B0`.
   Добавлено после того, как я сам оценивал спрайты на фоне, почти совпадавшем
   с цветом поддоспешника, и тёмные части просто не читались.

**Отдельно про листы согласования.** Полосы кадров рисовались на холсте
фиксированной ширины 1520 px, и всё, что не влезало, обрезалось: у `walk` и
`run` не было видно к6–к7, у `reload` — половины кадров. Атласы и JSON при этом
были правильными, дефект был только в презентации. Починено в `sheet_anim.py`:
полосы переносятся по строкам, ширина листа считается по содержимому. Все листы
перерисованы.

## 7г. Проверка интеграции

`sfml_example.cpp` — не псевдокод, а собираемый и запускаемый референс:

```
g++ -std=c++17 sfml_example.cpp -o demo -lsfml-graphics -lsfml-window -lsfml-system
```

Собран и прогнан на SFML 2.6.1 без предупреждений. Весь используемый API
одинаков в 2.5.1: `setTextureRect`, `setOrigin`, `setRotation`,
`Shader::setUniform`. В примере закрыты все механики этапов: выбор строки
кувырка от угла между рывком и прицелом, `weapon_offset` и `move_speed`,
столбец варианта хвата на перезарядке, слои крови в правильном порядке,
шейдер попадания, заморозка угла трупа, шесть типов противников.

Прогон вскрыл ошибку, которой не было видно на листах: в первой версии
примера я вычитал из `muzzle_offset.y` двенадцать пикселей, считая, что
смещение задано от оси ствола. Оно задано **от пивота тела**, и вспышка
уезжала внутрь оружия. Теперь таблица стволов в примере генерируется прямо
из `weapons.json`, а расхождения между кодом и JSON проверяются скриптом.

Константы раскладки в примере продублированы намеренно: он не тащит
json-библиотеку. В боевом коде читайте `character.json`.

## 8. Подключение в SFML 2.5.1

```cpp
bodyTex.setSmooth(false);            // критично: иначе поворот превратится в кашу
wpnTex.setSmooth(false);

body.setOrigin(32.f, 32.f);          // пивот тела
weapon.setOrigin(80.f, 32.f);        // пивот оружия — та же мировая точка

float angle = std::atan2(aim.y - pos.y, aim.x - pos.x) * 180.f / 3.14159265f;

body.setTextureRect({frame * 64, row * 64, 64, 64});
body.setPosition(pos);  body.setRotation(angle);  rt.draw(body);

weapon.setTextureRect({0, weaponRow * 64, 160, 64});
weapon.setPosition(pos); weapon.setRotation(angle); rt.draw(weapon);
```

Рендерить сцену в `sf::RenderTexture` нативного размера и растягивать целым
множителем (×2, ×3) — иначе пиксель перестанет быть квадратным.

Дульный срез: взять `muzzle_offset` из `weapons.json`, повернуть на `angle`,
прибавить к позиции персонажа.
